## 2. 检索方案 → BM25-lite 路线的实证与边界

- **keyword(BM25) 对描述型工具名/description 简单有效；embedding 在 <500 条 + 零依赖约束下复杂度不划算**（v2 决策，MCP Client Best Practices 与 Reddit 140 工具实战同结论；本机 237 条同规模）。
- v3 实测补充（本机真实清单回归发现的三类 keyword 检索固有缺陷与正解）：
  1. **词表鸿沟**：「查A股行情」↔ 触发词「股票」——bigram 切不出桥接词。正解 = **人工别名层**（`cap.mjs alias` 灌 `manual.aliases`，匹配时触发面并入 + 别名整词覆盖强加分），而非堆权重。这正是 MCP 官方「model-controlled discovery」留给客户端策展的空间。
  2. **长描述刷分**：automation 条目 500 字 prompt 里泛词 bigram 靠词数累积压过特异触发词（实测 34 vs 9）。正解 = **desc 命中每条目封顶 3 token**。
  3. **边界字假命中**：单字「调」桥接到「调用方式」。正解 = **单字 CJK 禁 contains 桥接**，只允许触发词全等。
  4. **事实型 vs 能力型**：env/hardware/software 是参考事实，任务意图命中时应让位于能力型条目（×0.85）。
- 参考面：Claude Skills「description 即触发器」惯例（本机 54 技能「触发词：」段实测），v2 已落 `extractTriggers`。

## 3. 环境能力建模 → SBOM 与 CMDB 的口径借鉴

- 软件清单走 **卸载注册表三视图**（HKLM/HKLM WOW6432Node/HKCU）并过滤 `SystemComponent` 与 KB 更新噪声——与 SBOM 工具（WinGet list / BrReturning 注册表枚举）同源口径；dev 工具链单独走 `where + --version`（注册表不覆盖 CLI 工具）。
- 硬件用 **WMI 单次采集**（Win32_Processor/VideoController/LogicalDisk/OperatingSystem），GPU **排除虚拟显示适配器**（本机实测 Todesk/OrayIdd/MuMu 三张虚拟卡 vs 一张实体卡——不排除会把远程桌面虚拟卡当 GPU 能力登记，误导算力判断）。
- 事实型条目 `invoke.kind='manual'` + 描述标「物理事实条目」——与 CMDB「属性 vs 能力」分层一致：插件登记事实，决策（如「要不要上云」）留给人（AGENTS.md 铁律 1）。

## 4. 定期巡检 → 官方「低频拉取」+ 本机双系统边界的合并口径

- MCP Registry 官方拉取频率「infrequent（~hourly）」→ 能力清单日级巡检足够（fingerprint 含 mtime/版本/内容 hash，日粒度变更不漏）。
- 本机两套定时系统边界（官方 `schedule_create` 投递回原会话 vs 第三方 `automation_create` 每次新 Session）——巡检用的是后者（已有 `automation_8fa49ea2` 每日 06:30），v3 扩覆盖新探针。
- 巡检纪律沿用 v2 定案：**只汇报不自动修复**（事实归 AI，决策归人）。
